Intention

Triage that is cheap, private, and gets better by itself.

On a gig-work marketplace, thousands of workers file tickets: a payment that has not arrived, a KYC document stuck, an app that crashes at login. Each ticket must land with the right team, at the right urgency, fast.

APayment delay
BPayment dispute
CKYC / onboarding
DTask assignment
EApp bug / login
FSubmission problems
GAccount suspended
HOther

Output per ticket is one category (A–H) and one priority (P1–P4). The owning team is a fixed lookup from the category.

The problem

Every obvious option fails somewhere.

01

Send everything to a frontier model

Accurate, but you pay for every ticket, wait on the network for every ticket, and ship worker data off-device every time. Cost scales linearly with volume.

02

Run a small model alone

Cheap and private, but it is wrong often enough to hurt, and it never improves because nothing teaches it.

03

Label data by hand

Good labels, slow loop. By the time a batch is labelled, the ticket mix has moved on.

04

Silent wrong answers

A mis-routed payment or KYC ticket is worse than a slow one. Any system that guesses without saying so is unsafe, and the cloud being down must not stop triage.

The solution

A loop where the expensive model trains the cheap one.

Understudy treats the cloud teacher as a coach, not a crutch. The local model works every ticket first and learns from every correction.

Route

Local model answers first

Gemma 4 E4B (4-bit, MLX, Apple silicon) reads the ticket and returns a category, a priority, and a confidence.

Teach

Teacher steps in when unsure

Below a calibrated threshold, the cloud teacher answers. Its answer is saved as a training example. If the teacher is unreachable, the ticket waits in a human review queue.

Train

LoRA round on the Mac

Saved teacher answers fine-tune a small LoRA adapter locally. No GPU rental. The serving model is unloaded during the round so only one model sits in RAM.

Gate

Promote only if it is better

The new adapter is scored on a held-out test set. It is promoted only if category macro-F1 strictly improves. Otherwise the old model keeps serving and the reason is stored.

How confidence works

Eight scores in, one honest probability out.

Before writing its answer, the model gives every possible next token a raw score, called a logit. We read only the eight scores for the category letters A–H.

softmax(logitA..H) → 8 probabilities that sum to 100%
confidence = probability of the chosen letter

The threshold is calibrated per model version: the lowest value that still gives at least 95% accuracy above it on the validation set. At or above it, the local answer stands. Below it, the teacher is asked.

Priority (P1–P4) comes from generated text and has no confidence score. Confidence gates the category only.

Architecture

Small pieces, one path for each job.

Blue: the local path. Orange: escalation to the teacher. Purple: human review. Green: the training and promotion loop. The dots are tickets and training data in motion.

One ticket, one pass

The prompt is processed once. The same pass produces the confidence and fills the cache that the priority is decoded from.

What went wrong, and what we did

Problems we hit, solutions that stuck.

Problem

The model crashed with “no Stream(gpu) in current thread” when called from web worker threads.

Solution

MLX streams are per thread, so loading and inference run on one dedicated MLX thread.

Problem

Training and serving both want the memory. Two models do not fit comfortably.

Solution

Serving pauses and unloads during a round, then hot-swaps to the new adapter. One model in RAM at a time.

Problem

Each ticket processed its prompt twice: once for confidence, once to generate the priority.

Solution

One forward pass fills a KV cache that decoding continues from. Median latency 548 → 378 ms (−31%) with identical confidences and equal-or-better accuracy against gold labels.

Problem

A new training round can make the model worse.

Solution

A strict macro-F1 gate. Round 1 reached 69.5% against a base of 76.1% and was rejected, with the reason stored.

Problem

Quick tunnels did not deliver server-sent events, so the live page froze.

Solution

A polling watchdog in the frontend. The backend also reports its real streaming state in /api/health, so the Stop button survives reloads.

Problem

The dashboard polled a query that loaded every ticket into Python.

Solution

The time series is aggregated in SQL with identical output.

Problem

Test labels come from the teacher, not from people, so scores can flatter the model.

Solution

Every score is flagged provisional until human gold labels replace them. We say so on the page and in the README.
